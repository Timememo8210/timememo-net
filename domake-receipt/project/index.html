01 / CONTEXT

Sky Portal 旧记录中的合作方是 Daniel Zhu。Domic 面向业主，积累维修、升级、设备和保修档案；ProLynk 面向服务撮合，已完成的服务文件可回流到房屋履历。本轮暂用用户提出的 Domake Receipt 作工作名，最终品牌拼写与生产域名需要和伙伴确认。

旧 Receipt Scanner 上传 → 编辑 → 预览 → 保存；实际只有浏览器 localStorage。 新原型明确写本地保存，同时保留原件；真实数据库下一轮接。

交互演示与实际文件明确分开：实际上传的文件不会被偷偷替换成示例结果。未接 AI 时，字段保持空白，用户可以手工整理。PDF 预览交给浏览器阅读器，没有自动提取文本或只读取第一页。

本地原型边界
文件与记录保存在当前浏览器。清理站点数据、无痕模式或存储被逐出可能导致丢失。JSON 不含二进制原件，应另下载原件。尚未连接 Domic 系统；确认成功不会宣称云端已保存。

原型按一份文件、一张逻辑单据、一个房屋活动整理。混合多张发票请先拆分。当前房屋名称是手工输入；生产改成有权限的房屋选择器。

03 / DATA CONTRACT

主界面只保留 9 组核心信息

最有价值的记录能回答：哪套房、什么时候、谁、在哪个部位、做了什么、多少钱、处于什么状态。其他字段不强迫用户填写。

信息 输出位置 没有时
归属房屋 property.id 草稿可空，确认前由用户填写；模型不得编造。
实际服务日期 service.date null；开票日期单独保留。
服务项目摘要 service.summary 确认前用户补充，说明实际或计划工作。
房屋系统 / 部位 service.category / location unknown / null。
服务商 provider.name null。
服务地址 property.service_address null；不能拿商家地址填空。
总金额 + 币种 amount.total / currency null，不默认为零或美元。
单据类型 document.type unknown；区分收据、账单、报价与保修文件。
付款 + 施工状态 amount.payment_status / service.completion_status unknown；付款和完工分开。

设备与保修值得保留，但不必展开

更多信息包括开票日期、单号、服务商电话/地址、费用明细、设备品牌型号与序列号、保修原文、施工许可编号及用户备注。将来可增添服务日期区间、税/折扣、维护周期、退款与材料购入状态。

三条语义规则
服务日期 ≠ 开票日期；服务地址 ≠ 商家地址；已付款 ≠ 已完工。报价可以保存为房屋资料，但不能当成已发生支出或已完成施工。

稳定结构，未知保留 null

{
  "schema_version": "1.0",
  "property": { "id": "用户确认的房屋", "service_address": null },
  "document": { "type": "invoice", "number": null, "issue_date": "2026-08-22" },
  "service": {
    "date": null, "category": "hvac", "summary": "空调年度保养。",
    "location": null, "completion_status": "unknown"
  },
  "provider": { "name": "Northline Heating · Fictional", "phone": null, "address": null },
  "amount": { "total": 189, "currency": "USD", "payment_status": "unknown" }
}

以上为核心字段节选，不是完整导出。完整记录还包含 items、details、source、evidence、review 与应用生成的时间信息。下载 完整 JSON Schema、完整缺失字段示例 和 字段与空值规范。

确认保存只强制房屋归属与工作摘要，其余允许未知并标记“待补全”。首次 AI 输出先成为草稿。错误、不可读文件与正常缺字段应分开；下一轮为缺失加入“未提供 / 看不清 / 歧义”原因。本轮金额用 JSON number，生产写入数据库时转换为定点金额。

04 / MODEL DECISION

先选低成本基线，再用真实票据决定

建议先比较 Gemini 2.5 Flash-Lite、3.1 Flash-Lite 和 3.5 Flash-Lite。2.5 Flash 与 3 Flash Preview 留作复杂样本对照。模型适配层独立，避免以后更换模型时重写上传与审核流程。

模型 每百万输入 / 输出 每万张预算* 角色
2.5 Flash-Lite $0.10 / $0.40 $4.90 最低价基线
2.5 Flash $0.30 / $2.50 $22.50 旧方案对照
3 Flash Preview $0.50 / $3.00 $30.50 复杂样本对照；Preview
3.1 Flash-Lite $0.25 / $1.50 $15.25 新一代低价候选
3.5 Flash-Lite $0.30 / $2.50 $22.50 质量对照候选

*2026-09-09 核对官方美元标准实时 API 价格。假设每张 2,500 输入 + 600 计费输出 token，一次成功，无额外 thinking / 重试 / 税 / 存储费。这是预算模型，未做实际模型调用。依据：Google 官方定价。

用户提到的“3.0 Flash”，这里对应的准确 ID 是 gemini-3-flash-preview。目前官方仍标 Preview；模型页与生命周期在正式部署前应再核对。Lite 候选均支持相关多模态/结构化输出，但文档能力不等于实际提取准确率。

把“免费功能”与“免费 API”分开考虑

面向真实票据建议使用关联结算账户的付费 API 条件：不要以免费层额度为长期产品容量或数据处理保证。Google 免费与付费服务的数据使用条款不同，地区也有例外；正式使用前按服务地区核对。Google API 条款。

单页实际等待时间需要测量，不承诺“2 秒识别”。建议测 p50/p95、人工改动率、关键字段编造率、重试率及每条确认记录总成本。后台历史批量导入可考虑 Batch；不能拿 Batch 折扣与最长周转时间做在线即时体验的承诺。Batch API。

05 / END-TO-END FLOW

成功要以用户确认和实际保存为准

添加文件→检查与预览→提取草稿→核对 / 修改→确认保存→房屋记录
情况 用户应看到什么
格式不支持 / 文件太大 说明允许格式和限制，保留已有工作；HEIC 提示转换。
真实 AI 尚未接入 明确说明未识别，允许手工填；不会制造“识别成功”。
未知日期 / 地址 / 金额 空值和待补全提示；可核对后保存不完整记录。
识别慢 / 429 / 503 / 超时 未来真实任务显示阶段、可取消、有限重试；不生成假进度，也不自动保存空结果。
同一文件再次添加 本地 hash 匹配后打开已有记录；跨设备与相似票据去重下一轮实现。
保存失败 不显示成功；保留表单，允许重试或导出草稿。
修改 / 退出 / 删除 未保存修改离开时提醒；修改更新原记录；删除需确认并删除对应原件。

原型含完整收据、缺日期发票、施工前报价三个案例，分别展示“信息齐全”“需要补充”“不能误判已完成”。验证涵盖字段规则、原型流程、持久化与失败恢复；尚未做真实模型评测或手机相机实机验收。

06 / IMPLEMENTATION

把识别、确认和保存分开

未来可以延续旧方案 Next.js + Supabase + 私有 R2，也可以接 Daniel 现有系统。当前为 TimeMemo 静态子页面，前端模块已经分开，输出结构不依赖某家模型。

网页 / 手机→上传与鉴权→模型适配器→结构校验→人工审核→数据库 + 原件

生产保留 properties、documents、activities、activity_documents、extraction_jobs、extractions、review_revisions。原件私有保存、短时授权访问。多个活动关联同一单据时，总金额只放单据一次，不能重复计入每项活动。

建议 API 按上传、创建识别任务、查询状态、保存草稿、确认、查看历史和删除拆开。确认请求带版本号与幂等键，服务端检查物业权限后事务保存，避免重试重复创建、并发覆盖或“成功但没入库”。

每张票据不需要运行多个自主 Agent；一个多模态提取服务、明确 schema、确定性校验与人审即可。多 Agent 本轮用于历史检索、模型研究和代码复核。

08 / NEXT ITERATION

下周和伙伴先确定这些事情

  1. 产品与接口：Domic / Domake 命名、已有后端仓库、物业 ID、用户鉴权、Daniel 接受的字段格式。
  2. 服务范围：爱尔兰 / 英国 / 美国、语言和币种；是否同时收录材料购置、保修、检查与退款。
  3. 样本评测：约 100 份经授权或合成票据，覆盖照片/PDF/多页/缺失/模糊/报价，人工建立答案；不要只跑空白模板。
  4. 模型与额度：用同一批样本对照 Lite 模型；根据人工修改率、耗时和总成本定默认模型与免费配额。
  5. 真实闭环：接服务端模型、私有文件、物业权限和事务保存，再做小范围真实用户试用。

后续再决定手机 App、邮件入口、ProLynk 自动传入、多人共享、房屋交接报告与维护提醒。这些都能沿用同一文档和活动结构，首轮先把上传到确认做好。
