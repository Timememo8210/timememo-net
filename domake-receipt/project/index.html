01 / CONTEXT

Domic Home Passport: from receipts to property history

The confirmed product name is Domic Home Passport. This is the receipt module of the original Home Passport project. The partner is Daniel Zhu. The aim is to build a lasting record of repairs, improvements, equipment, and warranties, with service documents from ProLynk.

Milestone Recovered context How it informs this iteration
May 2026 A digital property passport accepting ProLynk documents, emails, and manually uploaded PDFs, organized in a property timeline. Keep property association and service history at the center of the product.
June 2026 Gemini 2.5 Flash, model tests, human confirmation, and a proposed Next.js / Supabase / R2 stack. Keep the model replaceable, with an independent output contract and clearly defined backend interfaces.
Original Receipt Scanner Upload → edit → preview → save. Records were stored only in browser localStorage. The new prototype clearly identifies local storage and retains original files. A real database comes next.

The historical tests eventually produced readable results for 13 PDFs: 12 were read directly as PDFs; one used its text layer after a 503 error. Most were blank templates, and only three had relatively complete amounts. This does not establish accuracy on real receipts. The new format removes zero values for unknown amounts, automatic USD defaults, and unsupported claims about increased property value.

Sources: ProLynk / Domic history · Daniel's workbench · Historical model tests · Original prototype. A standalone live Domic Home Passport interface and Daniel's current production APIs have not yet been located.

Sample demonstrations and your own documents are handled separately: your uploaded file is never replaced with sample results. Until AI is connected, fields remain blank for you to complete. PDFs use the browser PDF viewer; the prototype does not automatically extract their text or process only the first page.

Local prototype limits
Files and records are stored in this browser. Clearing site data, using private browsing, or browser storage eviction may cause data loss. JSON exports do not include the original binary files; download those separately. The prototype is not connected to the Domic Home Passport backend, and save confirmations refer to local storage.

The prototype treats each file as one logical document and one property activity. Split combined invoices before adding them. Property names are entered manually for now; production will use a property selector governed by access permissions.

03 / DATA CONTRACT

Nine core groups of information

A useful record answers: which property, when, who, where in the home, what work, how much, and what status. Other fields are optional.

Information Output field When missing
Property property.id May be empty in a draft. The user supplies it before confirmation; the model must not invent it.
Service date service.date null; the invoice date is stored separately.
Work summary service.summary The user completes it before confirmation, describing actual or planned work.
Home system / location service.category / location unknown / null.
Service provider provider.name null.
Service address property.service_address null; do not substitute the provider's address.
Total + currency amount.total / currency null; never default to zero or USD.
Document type document.type unknown; distinguish receipts, invoices, quotes, and warranty documents.
Payment + work status amount.payment_status / service.completion_status unknown; payment and completion are separate.

Keep equipment and warranty details optional

Additional details include the invoice date, document number, provider phone and address, line items, equipment brand, model and serial number, original warranty wording, permit number, and user notes. Future extensions can cover service date ranges, tax and discounts, maintenance intervals, refunds, and material purchases.

Three rules for interpreting a document
Service date ≠ invoice date. Service address ≠ provider address. Paid ≠ completed. Quotes can be retained as property documents, but must not count as incurred expenses or completed work.

A stable structure, with null for unknown values

{
  "schema_version": "1.0",
  "property": { "id": "user-confirmed-property", "service_address": null },
  "document": { "type": "invoice", "number": null, "issue_date": "2026-08-22" },
  "service": {
    "date": null, "category": "hvac", "summary": "Annual air-conditioning service.",
    "location": null, "completion_status": "unknown"
  },
  "provider": { "name": "Northline Heating · Fictional", "phone": null, "address": null },
  "amount": { "total": 189, "currency": "USD", "payment_status": "unknown" }
}

This is an excerpt of the core fields, not a complete export. Full records also contain items, details, source, evidence, review, and timestamps generated by the application. Download the complete JSON Schema, full example with missing fields and field and missing-value specification.

Only the property and work summary are required to confirm a record. Other values can remain unknown and be marked as incomplete. Initial AI output becomes a draft. Errors, unreadable files, and ordinary missing fields need distinct handling; the next iteration will add missing-value reasons such as not provided, illegible, and ambiguous. Amounts are JSON numbers in this prototype and should be converted to fixed-point values for production database storage.

04 / MODEL DECISION

Start with a low-cost baseline, then test real receipts

First compare Gemini 2.5 Flash-Lite, 3.1 Flash-Lite, and 3.5 Flash-Lite. Use 2.5 Flash and 3 Flash Preview as comparisons for difficult samples. An independent model adapter allows models to change without rewriting upload and review flows.

Model Per 1M input / output tokens Budget per 10,000 documents* Role
2.5 Flash-Lite $0.10 / $0.40 $4.90 Lowest-cost baseline
2.5 Flash $0.30 / $2.50 $22.50 Comparison with the original choice
3 Flash Preview $0.50 / $3.00 $30.50 Difficult-sample comparison; Preview
3.1 Flash-Lite $0.25 / $1.50 $15.25 Newer low-cost candidate
3.5 Flash-Lite $0.30 / $2.50 $22.50 Quality comparison candidate

*Official standard real-time API prices in USD, checked on 9 September 2026. Assumes 2,500 input tokens and 600 billed output tokens per document, one successful attempt, and no additional thinking, retry, tax, or storage costs. This is a budget estimate; no live model calls were made in this round. Source: Google pricing.

The model referred to as “3.0 Flash” corresponds here to the exact ID gemini-3-flash-preview. It is still officially marked Preview. Recheck the model page and lifecycle information before production deployment. The Lite candidates support the relevant multimodal and structured-output capabilities, but documented capabilities do not establish real extraction accuracy.

A free user feature still needs an API budget

For real receipts, use the paid API terms associated with a billing account. Free-tier quotas should not be treated as a long-term capacity or data-processing guarantee. Google's free and paid services have different data-use terms, with regional exceptions; review the terms for the service region before production use. Google API terms.

Measure actual waiting time per page before making a speed promise. Track p50/p95 latency, the rate of manual corrections, fabricated critical fields, retries, and total cost per confirmed record. Batch processing may suit background imports of historical documents; its discounts and turnaround window should not be used to promise an instant online experience. Batch API.

05 / END-TO-END FLOW

Success means the user has confirmed and the record is saved

Add a file→Check and preview→Extract a draft→Review / edit→Confirm and save→Property records
Situation What the user should see
Unsupported format / file too large Explain accepted formats and limits while preserving existing work. Ask for HEIC conversion where needed.
Live AI is not connected State that extraction has not run and allow manual entry. Do not show a false extraction-success message.
Unknown date / address / amount Show missing values and completion prompts. Allow an incomplete record to be reviewed and saved.
Slow extraction / 429 / 503 / timeout Future live tasks should show their current stage, support cancellation, and limit retries. Do not fabricate progress or automatically save empty results.
The same file is added again Open the existing record when the local file hash matches. Cross-device and similar-document duplicate detection are planned next.
Save failed Keep the form without showing success. Allow a retry or draft export.
Edit / leave / delete Warn before leaving with unsaved changes. Edits update the existing record. Deletion requires confirmation and removes the associated original file.

The prototype includes three cases: a complete receipt, an invoice with a missing date, and a quote issued before work begins. They show complete information, missing information, and work that must not be marked completed. Verification covers field rules, prototype flows, persistence, and failure recovery. Live model evaluation and testing with a physical phone camera have not yet been completed.

06 / IMPLEMENTATION

Separate extraction, confirmation, and storage

Production could follow the original Next.js + Supabase + private R2 proposal or integrate with Daniel's existing system. The current prototype is a static TimeMemo subpage with separate frontend modules and a model-independent output structure.

Web / mobile→Upload and authentication→Model adapter→Schema validation→Human review→Database + original files

Production data objects include properties, documents, activities, activity_documents, extraction_jobs, extractions, and review_revisions. Originals remain private with short-lived authorized access. When several activities link to the same document, store the total once on the document; do not count it again for every activity.

Use separate API operations for upload, extraction-job creation, status checks, draft saving, confirmation, history, and deletion. Confirmation requests should include a version and an idempotency key. The server checks property permissions and saves in a transaction to prevent duplicate records on retry, concurrent overwrites, or success responses without a saved record.

Each receipt can be handled by one multimodal extraction service, a clear schema, deterministic validation, and human review. Multiple agents were used in this iteration for historical research, model research, and code review; they are not required for every receipt.

08 / NEXT ITERATION

What to agree with your partner next week

  1. System and APIs: the existing backend repository, property IDs, authentication, and Daniel's accepted field format.
  2. Service scope: the current intended audience is in the Arab region, with English as the default interface and a Chinese option. Confirm the initial launch countries and currencies with the partner; do not assume a currency or tax treatment. The earlier Ireland / UK / US sequence is historical context. Also agree whether to include material purchases, warranties, inspections, and refunds.
  3. Sample evaluation: around 100 authorized or synthetic documents covering photos, PDFs, multiple pages, missing values, blur, and quotes, with human-labeled answers. Include real document variety rather than relying on blank templates.
  4. Models and quotas: compare the Lite models on the same samples. Choose the default model and free user allowance based on manual correction rates, latency, and total cost.
  5. Production flow: connect server-side extraction, private file storage, property permissions, and transactional saving, then run a small pilot with real users.

Later decisions include a mobile app, email intake, automatic ProLynk imports, sharing, property handover reports, and maintenance reminders. These can reuse the same document and activity structure. The first iteration focuses on the flow from adding a document through confirmation.
