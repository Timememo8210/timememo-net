# Domic Home Passport：字段、审核闭环与可复用资源研究

研究日期：2026-09-09。用途：供 Domic Home Passport 房屋历史票据录入原型与伙伴交接使用。以下字段与产品行为是针对本项目的设计建议；仓库功能及许可证已通过一手 GitHub 页面、LICENSE 文件和 GitHub API 核对。本次只做资料研究，没有安装外部 skill，没有复制外部代码，也没有对这些仓库进行运行测试。

## 1. 建议的产品定义

把上传的文档转成「有原始凭证、可核对、可修正的房屋维护记录」。一张维修发票的价值并不止于支出金额，还包括这栋房子何时修过什么、由谁做、涉及哪个系统或设备，以及以后索赔、保养或转售时能否找到凭证。

因此应保留两层：**文档**是事实来源，**房屋活动记录**是用户确认后的整理结果。它们通常一对一，但一张发票可以包含多个服务，一次维修也可以有报价、发票、付款凭证、保修卡等多份文档。第一版界面可以简单，数据关联不要把两者锁死成一对一。

最容易损害房屋历史可信度的错误是：把开票日期当成施工日期，把商家地址当成房屋地址，把报价当成已完成施工，以及同一项目多份单据重复累计费用。这四项应比逐行商品识别优先解决。

## 2. 最小主表单：9 组信息

| 界面字段 | 建议字段 | 为什么保留 | 没有时的处理 |
|---|---|---|---|
| 归属房屋 | `property_id` | 房屋历史的主键，由用户在自己的房屋中选择 | 草稿可空；正式归档前必须确认；不能让模型编造 ID |
| 服务日期 | `service_date_start`、`service_date_end` | 记录工作发生的日期或区间 | `null`；另显示开票日期，不冒充服务日期 |
| 做了什么 | `summary` | 一句话描述本次工作，避免只写「服务」 | 用户补充后可归档；没有服务证据时按文档实际性质描述 |
| 系统／部位 | `category`、`location_detail` | 按屋顶、暖通、管道等组织房屋历史 | `category: "other"` 或 `"unknown"`，部位 `null` |
| 服务商／商家 | `provider_name` | 后续联系、维修追踪与凭证查询 | `null`，保留待补全标记 |
| 服务地址 | `service_address` | 验证凭证与房屋是否对应 | `null`；用户仍可手动确认归属房屋，不能复制商家地址填空 |
| 金额与币种 | `total_amount`、`currency` | 保留原币种的凭证金额 | 两者可以 `null`；不填 0，不默认美元 |
| 单据性质 | `document_type` | 区分收据、发票、报价、工单等 | `"unknown"`，提示用户确认 |
| 付款／工作状态 | `payment_status`、`activity_status` | 已付款不等于工作已完成；购入材料不等于已安装 | `"unknown"`；只有证据或用户确认才能升级 |

主表单可以用两列紧凑布局；将「开票日期、单号、明细、税费、设备、保修、备注」放在可展开的更多信息中。不要要求每张单据填写所有扩展字段。

**归档要求建议：**用户已选择有权访问的房屋、确认或补充摘要、核对来源文档，即可保存不完整记录；未知日期、商家或金额不应阻止保留真实凭证。保存为「已归档 · 信息待补全」，而非声称全部信息准确。任何尚未经过用户确认的模型结果都保持草稿状态。

建议首版分类枚举：`hvac`、`plumbing`、`electrical`、`roof`、`appliances`、`structure`、`interior`、`exterior`、`landscaping`、`pest_control`、`safety_security`、`cleaning`、`other`、`unknown`。类别是整理标签，并不是施工内容的证明。

## 3. 后续生产扩展候选格式（非本轮 v1 导出契约）

前端确认表单保持简洁；导出结构稳定。下面是 **生产扩展候选草稿示例**，所有姓名、地址与金额均为合成演示数据，不是用户真实收据。保留固定键，提取不到的值写 JSON `null`。`source`、`property_id`、`review` 由应用维护，模型仅填 `document`、`activity` 并提供字段证据，不能替应用决定归档状态。

```json
{
  "schema_version": "1.0",
  "record_id": "draft_demo_001",
  "property_id": "property_demo_01",
  "source": {
    "document_id": "document_demo_001",
    "file_name": "sample-hvac-invoice.pdf",
    "page_count": 2
  },
  "document": {
    "document_type": "invoice",
    "document_number": "DEMO-1042",
    "issue_date": "2026-09-03",
    "provider_name": "Example Home Services",
    "total_amount": "418.00",
    "currency": "USD",
    "payment_status": "paid"
  },
  "activity": {
    "service_date_start": "2026-09-01",
    "service_date_end": null,
    "summary": "更换暖通风机电容并检查运行情况",
    "category": "hvac",
    "location_detail": "阁楼暖通设备",
    "service_address": "100 Example Lane, Example City, CA 90000",
    "activity_status": "completed",
    "notes": null
  },
  "details": {
    "line_items": [],
    "equipment": [],
    "warranty": null
  },
  "review": {
    "status": "needs_review",
    "warnings": []
  }
}
```

实现约定：

- `record_id`、`document_id` 为应用生成的不可猜测 ID；示例 ID 只用于演示。
- 日期使用 `YYYY-MM-DD`，按单据当地日期保存为日期类型，不转换成会跨日的 UTC 时间戳。日期区间保留起止；只有月份或年份时不伪造某月 1 日，日期值留空，原文保存在证据元数据中。
- 金额使用十进制定点字符串，如 `"418.00"`，数据库使用 `DECIMAL`；前端可作为金额输入。币种使用明确的三字母代码。`$` 本身可能对应多个币种，无法确认时保留 `null` 并提示。数值解析要处理 `1,234.56` 与 `1.234,56` 的地区差异。
- `document_type`：`receipt | invoice | estimate | work_order | warranty | refund | other | unknown`。
- `payment_status`：`paid | partial | unpaid | refunded | not_applicable | unknown`。不能因为标题写着 Invoice 就断言未付款；也不能因为看起来像收据就假设付款已经完成。
- `activity_status`：`proposed | scheduled | completed | purchased | unknown`。材料购买用 `purchased`，没有安装记录就不能变成 `completed`。
- `review.status`：`needs_review | saved | rejected`，是应用状态，不是模型置信度。补全程度另算，避免一个字段同时表示「已经保存」和「内容完整」。
- `details` 是扩展区。`line_items: []` 表示提取流程完成后没有可用明细，不表示确认金额为零。如果整页不可读、整次提取失败，使用顶层处理状态和告警表达，不返回貌似成功的空记录。
- 更详细的付款信息，可增加 `amount_paid`、`balance_due`，但仅在单据明确记载时填写。总额、已付金额、待付余额分开，不用其中一个覆盖另一个。
- 退款文档明确保留 `document_type: "refund"`。若将来做支出统计，另设统一的交易方向或符号规则，不凭负号猜测用户收到退款，也不把原发票和退款当作两笔正支出。

### 内部证据元数据

证据不要塞入每个输入框，也不要让用户被复杂 JSON 淹没；独立保存到 `field_meta` 或审核记录。建议结构：

```json
{
  "field_path": "activity.service_date_start",
  "value_state": "present",
  "source_kind": "document",
  "page": 1,
  "raw_text": "Service completed: September 1, 2026",
  "review_reason": null,
  "human_verified": false
}
```

`value_state` 可为 `present | not_present | unreadable | ambiguous | not_applicable`。`source_kind` 可为 `document | user | derived`。模型填写的页码、原文也需能在原始文档中复核；没有可验证的边界框时不要伪造精准定位。保留模型初始值、用户最终值、修改时间及审核人，便于复查和后续评测。

例如：服务日期未出现时，值为 `null`，元数据为 `not_present`；印迹不清时为 `unreadable`；`03/04/2026` 无法判断月日顺序时为 `ambiguous`。界面分别显示「单据未提供」「看不清」「需要确认」，不能把这些问题都混成一个空格。模型自报的 0.97 不是已验证的 97% 准确率；首版优先展示明确的检查原因与证据，不用漂亮但未经校准的百分比制造信任。

### 房屋领域值得保留的扩展信息

| 信息 | 优先级 | 提取边界 |
|---|---|---|
| 设备品牌、型号、序列号 | 高 | 出现在原文时提取；以后保养、换件和召回查询有价值 |
| 保修期、到期日期、范围、条款原文 | 高 | 「一年保修」与明确到期日分开；未明确起算日期时不要自行算到期日 |
| 工作部位／房间 | 高 | 厨房、主浴、阁楼等，比笼统地址更有维护价值 |
| 维修前问题、完成工作、建议后续动作 | 中 | 明确区分已经做了什么与建议以后做什么 |
| 下次保养日期／频率 | 中 | 只提取明确记载；模型常识建议应显示为另外的建议内容 |
| 人工费、材料费、税费、折扣、明细 | 中 | 可展开；不以完整明细为首版成功前提 |
| 服务商电话／邮箱、许可证号、工单号 | 中 | 原文出现才存；不自动声称服务商执照已验证 |
| 施工许可／检查结果及关联编号 | 中 | 是后续重要凭证；不能把普通发票当作许可或验收证据 |

## 4. 地址、重复文档、长 PDF 与多服务的处理

### 地址匹配

先将文档中的服务地址、账单地址、商家地址作为不同角色识别。只有服务地址可以直接参与房屋匹配。标准化街道缩写、大小写、空格可用于候选匹配，但保留原文与单元号。不能因为 ZIP 相同、街道相似或用户只有一套房就自动认定匹配成功。

推荐 UI：上传前已有当前房屋上下文；识别后提示「地址与当前房屋相符／地址不同／单据没有服务地址」。后两者让用户在确认页选择正确房屋或确认归属，模型不能覆盖已有房屋地址。账号无权访问的房屋 ID 不可被写入，权限判断在服务端执行。

### 重复上传

1. 同一用户或组织内，上传文件的 SHA-256 相同：直接提示已上传，打开原草稿／记录，避免重复模型费用；除非用户显式要求重新识别。
2. 文件不同但商家、单号、日期、金额、币种等吻合：标记疑似重复，供用户比较，不自动删除。
3. 同一项目的报价、发票和付款凭证：通常是互补资料，应可关联到同一活动，不能一律当作重复；支出统计按确定的费用记录计算一次。
4. 上传、重试、确认保存都带应用生成的幂等键。网络超时后的重试不得生成第二条房屋记录。后端用事务和唯一约束保证，不能只靠按钮禁用。

### 多页和多个独立文档

- 首版可以明确限制，例如每个文件最多 10 页、20 MB；这是产品限制的建议值，须与模型和基础设施实际限制区分。界面在上传前显示限制。
- 长 PDF 先展示页数，允许用户选择相关页，或要求拆分；不要只处理第一页或前几页却显示全部成功。
- 一份两页发票是一个文档，两张发票扫描成同一 PDF 是两个逻辑文档。需要保留页面范围与文档分组；识别到多个独立单据时先拆分审核或明确引导用户拆分。
- 长文档批处理时保留页面来源、分组标识和失败页；某组失败不会丢掉已完成组。覆盖所有页之后才能报告全部完成。
- 多个独立单据使用 `documents[]`；一个单据中不同工作使用 `activities[]`。不要强行展开成一个巨大的 summary。
- 同一张发票内如果有空调保养与水管维修，可生成两个活动，分别关联同一 `document_id`；文档总额只存一次。无法准确分配的活动金额保持空值，不能把总额复制给每个活动。

第一版若只支持单文档单活动，应在界面和 API 契约中明确写出这个边界，并把检测到的多文档、多活动转入人工处理，不能静默合并。后续数据库推荐 `documents`、`activities`、`activity_documents`、`extractions`、`review_revisions` 五类对象；是否物理拆表由伙伴按技术栈决定。

## 5. 从上传到数据库的完整闭环

```text
选择房屋 → 选文件／拖入文件 → 文件校验与预览
  → 上传完成 → 排队／识别中 → 类型与字段提取
  → 结构校验＋日期／金额／地址／重复检查
  → 可编辑的审核页 → 用户确认保存
  → 保存成功 → 房屋历史中可查看原文、编辑、导出
```

「上传成功」「识别完成」「保存成功」是三个不同结果。只有数据库确认成功才能显示最后一步的成功提示。原型如果只存在浏览器，必须明确写「已保存到此浏览器」；如果是样本演示，不能把它包装成已完成真实 AI 识别。

| 发生情况 | 用户应看到 | 下一步 |
|---|---|---|
| JPG／PNG／PDF 正常 | 原文件预览、识别进度、可编辑结果 | 用户核对后保存 |
| iPhone HEIC 或其他未支持格式 | 明确说明格式尚不支持，保留返回入口 | 转成支持格式再上传；后续再加服务端转换 |
| 文件太大／超页数 | 告知实际大小／页数与允许值 | 选择页、拆分或重新选择文件 |
| 密码 PDF／损坏文件 | 说明原因，不能一直转圈 | 上传无密码版本或换文件 |
| 模糊、裁掉金额或日期 | 具体字段提示「看不清」并保留其他结果 | 换清晰图或手工填写 |
| 不是目标文档 | 说明识别到的文档类型 | 改选文件或选择手工录入 |
| 模型超时、429、服务失败 | 当前步骤、可重试按钮；保留文件和已编辑内容 | 有限次数后台重试，失败后手工录入 |
| 模型 JSON 不合格 | 避免直接把异常堆栈显示给用户 | 一次受控重试；再失败进入空表单并保留原文 |
| 金额计算不符 | 标注原文总额与计算差异 | 用户核对，不能自动替换印刷总额 |
| 用户取消／返回 | 已填写内容作为草稿保留 | 回来继续，不强迫重新识别 |
| 确认保存失败 | 明确「尚未保存」，保留全部编辑 | 重试保存，幂等避免重复 |
| 确认保存成功 | 摘要、归属房屋、状态与查看记录入口 | 可再上传、查看原文、编辑或导出 |

桌面审核页用「左边原文、右边字段」，手机用可切换的原文／字段视图。不要把全部复杂编辑挤进无法滚动的小弹窗；可以使用大抽屉或独立确认页，保存后再弹出简洁的成功提示。键盘可访问、上传与保存状态可被读屏识别、错误焦点落到相应字段，应从首版设计。

图片重新上传时，已被用户修改的字段不可被模型静默覆盖；展示新旧差异并允许用户采用新识别值。AI 识别只产生草稿，这也使后续手机拍照入口可以沿用同一个后台流程。

## 6. GitHub 可借鉴项目：5 个，边界明确

### A. Receiptor-AI/bookkeeping-skills — 可借鉴流程与 skill 结构

提供 `receipt-processing` skill，包含固定输出字段、原始凭证引用、异常处理和审核流程，也有独立的输出结构参考文件。代码仓库采用 MIT。适合借鉴「提取—校验—异常队列—可审核导出」的组织方式。它以记账为领域，房屋归属、服务日期、设备和完工状态需要我们自行设计；不能照搬其税务分类或邮件优先策略。其商业 Receiptor 服务不等于仓库里自带的免费 OCR 引擎。[仓库](https://github.com/Receiptor-AI/bookkeeping-skills) · [receipt-processing 源文件](https://github.com/Receiptor-AI/bookkeeping-skills/blob/main/skills/receipt-processing/SKILL.md) · [输出结构](https://github.com/Receiptor-AI/bookkeeping-skills/blob/main/skills/receipt-processing/references/OUTPUT-SCHEMA.md) · [MIT 许可证](https://github.com/Receiptor-AI/bookkeeping-skills/blob/main/LICENSE)

**采用建议：**参考其文档分层，为伙伴提供本项目自己的提取说明、JSON Schema、样本和人工校正规则。无需为了网页功能安装整套记账技能。

### B. invoice-x/invoice2data — 可作为高频固定供应商的低成本路径

Python 工具支持 PDF 文本／OCR 后端、YAML／JSON 正则模板、CSV／JSON／XML 输出，当前仓库也说明存在可选 AI fallback。MIT。适合频繁重复且格式固定的服务商发票；针对千奇百怪的用户照片，维护大量模板的收益需要先验证。[仓库](https://github.com/invoice-x/invoice2data) · [MIT 许可证](https://github.com/invoice-x/invoice2data/blob/master/LICENSE.md)

**采用建议：**首版不把模板引擎设为必经步骤。以后若某供应商占上传量很大，可增加模板快捷处理并用同一个 Domic Home Passport 结构输出；失败仍走多模态提取。

### C. Docling — 可选的复杂 PDF 预处理组件

支持多种文件格式、PDF 布局／表格理解、OCR，以及统一文档表示和 JSON 等导出；可在本地运行。主代码 MIT，具体模型需要分别核对原始模型许可。它处理的是文档结构，不会自动决定房屋历史业务字段。[仓库](https://github.com/docling-project/docling) · [MIT 许可证](https://github.com/docling-project/docling/blob/main/LICENSE)

**采用建议：**作为以后复杂、多页 PDF、布局证据或私有部署的备选。普通照片和短 PDF 先直接调用多模态模型，避免引入本地 OCR 环境、模型下载和额外处理时间。

### D. Instructor（现仓库 567-labs/instructor）— 可选的 Python 结构化提取层

## 7. 第一轮给伙伴的验收与架构建议

**原型可以完成：**网页文件入口、照片／PDF 预览、固定字段审核、缺失与错误状态、手工修改、保存结果、历史列表、原文关联、JSON 导出及示范案例。如果尚未接后端 AI，要显著标注演示数据与本地保存边界，不宣称任意用户文件已经被 AI 正确读取。

**真正给用户试用前需要：**服务端模型调用与密钥、文件私有存储、权限校验、数据库持久化、上传／任务／确认保存接口、有限重试、配额及成本记录。公开网站中只能发布合成样本与项目说明，不能将用户真实房产地址、收据图片和 API Key 提交到公开 GitHub 或静态资源目录。

建议接口分工：上传取得 `document_id`；创建提取任务取得 `job_id`；前端查询任务状态并拿草稿；用户提交修改与确认；保存接口校验权限和幂等键后一次性落库。提取服务不得直接写最终房屋历史记录，也不需要自由调用工具的多 agent 运行时；多 agent 更适合此次研究与开发阶段。

建议先准备 60–100 份经授权或合成的评测文件，包含清晰照片、模糊照片、手机截图、数字 PDF、扫描 PDF、服务日期与开票日期不同、报价、部分付款、材料购买、保修、重复上传、多页及混合文档。保留一部分未参与调提示词的测试集。这个样本量是启动建议，不是达到生产准确率的统计保证。

单独记录关键字段准确率、关键字段被编造比例、需要修改的字段数、确认耗时、首次成功率、失败后可恢复率、每文档实际费用及延迟分布。服务日期、房屋匹配、金额币种、文档类型和工作状态需要比普通分类标签更高的优先级。模型自评不能代替人工标注的正确答案。

金额校验只在有足够组成项时进行。缺少折扣、附加费用或税项时不要判定错误；有差异就显示原始数值与计算值，不自动重写总额。文档内容一律当作待提取数据，其中任何「忽略规则」「调用网址」等文字都不应改变服务端提取指令或获得额外权限。

## 8. 需要与用户／伙伴讨论的产品选择

1. 第一期是否只做维修保养，还是同时收录购置材料、装修、清洁、保修和检查报告？建议允许不同文档类型，主时间线清楚标明状态。
2. 同一用户是否有多套房屋、共享业主或租客？这影响房屋选择与数据权限，建议原型从一套房屋开始但保留 `property_id`。
3. 缺服务日期／金额时是否仍能保存？建议允许，显示待补全，避免迫使用户或模型猜填。
4. 伙伴现有系统接受什么 API／字段？本报告给的是独立稳定契约，可再建立一层字段映射，不让模型直接输出未知内部系统格式。
5. 单文档最大页数、免费额度、付费／免费模型路由，以及长期保存原件的期限如何确定？要用真实样本费用与延迟结果决定。
6. 第一期是否支持一票多活动？若暂不支持，务必让用户知道，并提供人工拆分／汇总方式。

这些问题不妨碍先完成可评审原型。默认建议为：英文和中文内容可提取；上传 JPG／PNG／PDF；用户选择房屋；每次先处理一个逻辑文档；全部结果先人工确认；固定结构 JSON 导出；缺失允许保存并标记；真实模型、数据库和私有存储的集成边界在页面说明中明确列出。
